# Python Console 퀴즈 게임: 객체 지향과 데이터 영속성 실습

Python 기초 문법, 객체 지향 프로그래밍(OOP), JSON 파일 입출력 학습을 위해 구현된 터미널 기반 대화형 퀴즈 게임 프로젝트입니다. 코드의 단순 구현을 넘어, **기술 도입 근거와 예외 처리에 중점을 두고 설계**되었습니다.

---

## 🎯 1. 기본 요구사항 충족 및 실습 증빙 (항목 1)

### Q. 프로그램 종료 후 재실행해도 추가된 퀴즈와 최고 점수가 유지되는가?
✅ **YES.** 데이터는 `state.json` 파일에 즉시 영속화(Persistence)되어, 프로그램을 강제 종료(Ctrl+C)하거나 재시작해도 이전 상태(새로 추가된 문제, 최고 점수)가 100% 복원됩니다.

### Q. 기본 퀴즈가 5개 이상 포함되어 있는가?
✅ **YES.** 파이썬 기초 상식을 묻는 5개의 기본 퀴즈(객체 지향, 메서드 등)가 내장되어 있으며, 데이터 파일이 아예 존재하지 않는 최초 실행 시 자동 로드됩니다.

### Q. GitHub 저장소 연동 및 브랜치 작업 흔적이 존재하는가?
✅ **YES.** 
- 10개 이상의 의미 있는 기능 단위 커밋(Commit)이 완료되었습니다.
- `git log --oneline --graph` 명령을 통해 `feature` 브랜치 파생 및 `main` 브랜치 병합(Merge) 기록을 확인할 수 있습니다. (하단 스크린샷 참고)
- `clone` 및 `pull` 명령어를 통한 로컬-원격 저장소 동기화 실습을 완료했습니다.

## 🏗️ 2. 코드 구조 및 설계 (항목 2)

### Q. `Quiz` 와 `QuizGame` 등 클래스들의 책임을 어떻게 나눴는지 설명할 수 있는가?
* **`Quiz` 클래스 (데이터 객체):** 개별 문제 1개의 '상태'(문제 지문, 4개의 선택지, 정답 번호)를 저장하고 관리하는 데이터 컨테이너 역할만 담당합니다.
* **`QuizGame` 클래스 (비즈니스 로직 및 상태 제어):** 게임의 '전체 흐름'(문제 출제 루프, 정답 채점, 점수 계산)을 관리하고, 여러 `Quiz` 객체들의 목록과 최고 점수를 보유하며, 파일 시스템(`state.json`)과의 I/O를 통제하는 중앙 관제탑 역할을 합니다.

### Q. "입력 처리(검증)", "게임 진행", "데이터 저장/불러오기" 로직을 어떤 기준으로 분리했는가?
철저한 **단일 책임 원칙(SRP)**에 따라 파일을 3개로 분리했습니다.
1. **입력 처리 (검증):** `helpers.py` 파일의 `read_int()`, `read_nonempty()` 함수가 전담합니다. 사용자 입력을 검증하는 코드(공백, 문자 등 예외 처리)를 게임 로직에서 완전히 분리했습니다.
2. **게임 진행 (로직):** `main.py`는 오직 '메뉴판 UI'만 렌더링하고, 실제 퀴즈를 출제하고 채점하는 복잡한 과정은 `quiz.py` 내부의 `play_quiz()` 메서드로 제어권을 위임(Delegation)했습니다.
3. **데이터 입출력 (영속화):** `quiz.py` 내부의 `load_state()`, `save_state()` 메서드만이 `state.json` 파일에 접근할 권한을 가집니다.

### Q. `state.json` 읽기/쓰기 흐름이 프로그램의 어디에서, 어떤 순서로 발생하는가?
* **읽기(Read):** 프로그램 시작 시 `main.py`에서 `game = QuizGame()` 인스턴스를 생성하는 순간, `__init__` 생성자가 자동으로 `load_state()`를 호출하여 가장 먼저 메모리에 데이터를 적재합니다.
* **쓰기(Write):** 데이터의 '상태'가 변하는 즉시 수행됩니다. 사용자가 **1) 퀴즈를 새로 추가했을 때(`add_quiz`)**, **2) 게임을 마치고 최고 점수를 갱신했을 때(`play_quiz`)**, **3) 게임을 정상 및 강제 종료할 때** `save_state()`가 호출되어 변경사항을 하드디스크에 기록합니다.

### Q. Ctrl+C 또는 EOF 상황에서 "안전 종료"를 위해 어떤 처리를 했는가?
`main.py`의 메인 루프를 `try-except (KeyboardInterrupt, EOFError)` 블록으로 감쌌습니다. 사용자가 퀴즈를 풀다가 강제로 터미널을 끄더라도 시스템이 Crash되는 대신, **종료 직전에 `game.save_state()`를 강제 호출(Hook)하여 진행 중이던 데이터를 잃지 않고 안전하게(Graceful) 파일에 기록한 뒤 종료**되도록 방어 로직을 구축했습니다.

### Q. 커밋을 어떤 단위로 나누었고, 커밋 메시지 규칙을 어떻게 정했는가?
코드가 '독립적으로 작동하는 하나의 기능'을 완성할 때마다 커밋했습니다. (예: 입력 검증 모듈 추가 완료, 백업 시스템 도입 완료 등). 메시지는 협업을 가정하여 말머리 규칙을 따랐습니다.
* `feat:` 새로운 기능이나 모듈 추가
* `fix:` 치명적 오류나 예외 처리 방어 코드 보완
* `docs:` README 등 기술 문서 작성 및 주석 수정

## 🛠️ 3. 핵심 기술 원리 적용 (항목 3)

### Q. 클래스를 사용한 이유는 무엇이며, 함수만으로 구현할 때와 어떤 차이가 있는가?
* **상태 오염 방지:** 만약 `def` 함수로만 코드를 짰다면 내 최고점수(`score`) 변수를 여러 함수에서 공유하기 위해 `global score`(전역 변수)를 남발해야 합니다. 이는 누군가 다른 곳에서 점수를 바꿔버리는 치명적 버그를 낳습니다.
* **데이터 캡슐화:** `QuizGame` 클래스를 도입하면, 내 점수(`self.best_score`)가 클래스라는 캡슐 안에 안전하게 보관됩니다. 오직 허락된 메서드들만 이 점수에 접근할 수 있어 버그 발생 확률이 획기적으로 줄어들고 코드의 응집도(Cohesion)가 극대화됩니다.

### Q. JSON 파일로 데이터를 저장하는 이유와 JSON 형식의 특징은?
JSON 포맷은 파이썬의 **딕셔너리(`{Key: Value}`) 및 리스트 구조와 1:1로 완벽하게 매핑**됩니다. 별도의 복잡한 데이터 가공(파싱) 없이 `json.dump()`와 `json.load()` 함수 단 두 줄만으로 메모리 상의 파이썬 객체를 텍스트로 직렬화(Serialization) 및 역직렬화(Deserialization) 할 수 있어 개발 효율이 가장 뛰어납니다.

### Q. 파일 입출력에서 `try-except`가 꼭 필요한 이유는? (실패 케이스)
파일 I/O는 런타임에 외부 자원(OS, 디스크)을 건드리기 때문에 항상 에러가 폭발할 가능성이 존재합니다.
* **읽기 실패:** 파일을 사용자가 몰래 지웠거나(`FileNotFoundError`), 메모장으로 열고 쉼표를 지워 JSON 포맷을 훼손한 경우(`JSONDecodeError`).
* **쓰기 실패:** 하드디스크 용량이 꽉 찼거나 접근 권한이 없는 경우(`OSError`, `PermissionError`).
* **결과:** `try-except`로 이 상황들을 묶어두지 않으면 프로그램은 즉시 에러를 뱉으며 뻗어버립니다(Crash). 예외 처리를 통해 에러를 무시하고 사용자에게 경고만 주거나, 기본 데이터로 복구하는 등의 생존(Fail-safe)이 가능해집니다.

### Q. `state.json` 데이터 구조(필드/중첩 구조)를 현재 형태로 설계한 이유는?
```json
{
  "best_score": 100,
  "quizzes": [
    { "question": "문제", "choices": ["1", "2", "3", "4"], "answer": 1 }
  ]
}
```
퀴즈 목록(`quizzes`)과 최고 점수(`best_score`)는 묶음의 차원이 다릅니다. 이 둘을 리스트 안에 평면적으로 섞어 넣으면 어떤 데이터가 점수이고 어떤 데이터가 문제인지 추적하기 어렵습니다. 따라서 최상위를 **하나의 딕셔너리(객체)**로 두고 두 데이터를 명확한 Key로 나누어(중첩 구조) 관리의 직관성을 높였습니다.

## 🚀 4. 심층 인터뷰 (항목 4)

### Q. 퀴즈 데이터가 1000개 이상으로 늘어난다면 현재 JSON 방식에 어떤 한계가 생기는가?
현재 코드는 게임 시작 시 **JSON 파일 안의 모든 데이터를 한꺼번에 RAM(메모리)에 적재(Load)**하는 방식입니다. 데이터가 1,000건, 10,000건으로 늘어나면 부팅 속도가 수 초 이상 걸리고 막대한 메모리가 낭비됩니다. 또한 1문제만 수정해도 파일 전체를 통째로 다시 덮어써야 하는 병목이 발생합니다.
* **해결책:** 이 시점부터는 파일 기반 JSON을 폐기하고 **SQLite 같은 관계형 데이터베이스(RDBMS)**로 전환하여, 전체 데이터 중 필요한 문제 5개만 `SELECT`로 조회해오고 수정된 부분만 `UPDATE` 하는 방식으로 아키텍처를 업그레이드해야 합니다.

### Q. `state.json` 이 손상되어 파싱에 실패한다면 어떤 대응이 가능한가? (3-Tier Fallback 도입)
시스템이 절대 죽지 않고 무중단(Zero-downtime)으로 복구되도록 **3단계 다중 방어 시스템(3-Tier Fallback)**을 구축했습니다.
1. **원본 저장:** 데이터를 저장할 때, 무조건 `state.json.bak` 이라는 백업 사본(Hook)을 하나 더 만들어 둡니다.
2. **백업본 복원 시도:** 만약 원본 `state.json` 파일이 손상(JSON 문법 오류 등)되어 불러오기에 실패하면, 시스템은 튕기는 대신 조용히 `state.json.bak` 파일을 읽어들여 유저의 퀴즈 데이터를 완벽히 살려냅니다.
3. **최후의 보루:** 사용자가 원본 파일과 `.bak` 백업 파일까지 모두 지워버리거나 훼손한 최악의 상황에는, 클래스에 내장된 '기본 퀴즈 5문항'(`load_default_quizzes()`)을 메모리에 강제 적재하여 퀴즈 게임 서비스가 멈추지 않고 계속 구동되도록 견고하게 설계했습니다.

### Q. "정답 채점 방식"이나 "선택지 개수" 요구사항이 바뀐다면 어느 파일부터 수정해야 하는가?
역할이 완벽하게 분리되어 있으므로 **오직 `quiz.py` 내부만 수정**하면 됩니다. 
* 선택지 개수 변경: `Quiz` 클래스의 생성자와 `add_quiz()` 반복문 횟수 수정
* 정답 채점 로직 (예: 주관식 텍스트 채점): `Quiz` 클래스의 `check_answer()` 문자열 비교 방식으로 수정
* 위와 같이 코어 로직(`quiz.py`)을 대대적으로 뜯어고치더라도, 사용자 화면을 보여주는 `main.py`나 입력 검증 모듈 `helpers.py`는 단 한 줄도 고칠 필요가 없습니다. 이것이 단일 책임 원칙(SRP)과 클래스 설계의 궁극적인 장점입니다.
